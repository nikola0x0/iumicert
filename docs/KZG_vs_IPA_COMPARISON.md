## Introduction

Verkle trees are a cryptographic data structure that combines the properties of Merkle trees with vector commitments, enabling extremely compact proofs of membership. The choice of underlying polynomial commitment scheme significantly impacts the security model, performance characteristics, and trust assumptions of the system.

This document compares two primary approaches:

- **KZG (Kate-Zaverucha-Goldberg)**: Pairing-based polynomial commitments
- **IPA (Inner Product Argument) + Pedersen**: Discrete log-based commitments

---

## Overview of Polynomial Commitments

Polynomial commitment schemes enable a prover to commit to a polynomial $f(x)$ and later prove correct evaluations at arbitrary points without revealing the entire polynomial.

### Core Properties

| Property | Description |
|----------|-------------|
| **Hiding** | Given a commitment and up to $t$ openings, one cannot determine $f$ at unqueried points |
| **Binding** | Computationally infeasible to create two valid openings at the same point with different values |

### Application to Vector Commitments

Given a vector $\mathbf{v} = [v_1, v_2, \ldots, v_n]$, we can create a succinct commitment by:

1. Interpolating a degree-$(n-1)$ polynomial $f$ such that $f(i) = v_i$
2. Committing to $f$ using a polynomial commitment scheme
3. Opening at index $i$ proves the value $v_i$

This forms the foundation of **Verkle trees**.

## KZG Polynomial Commitments

### Mathematical Foundation

KZG operates over groups with an efficiently computable **bilinear pairing**:

$$e: \mathbb{G}_1 \times \mathbb{G}_2 \rightarrow \mathbb{G}_T$$

where $\mathbb{G}_1$, $\mathbb{G}_2$, and $\mathbb{G}_T$ are abelian groups of prime order $q$.

The bilinear property states:

$$e(a \cdot x, b \cdot y) = e(x, y)^{ab}$$

for all $x \in \mathbb{G}_1$, $y \in \mathbb{G}_2$.

### Trusted Setup

KZG requires a **structured reference string (SRS)** generated by a trusted party:

$$\text{SK} = \alpha \xleftarrow{\$} \mathbb{Z}_q$$

$$\text{PK} = \langle g_1, \alpha \cdot g_1, \alpha^2 \cdot g_1, \ldots, \alpha^t \cdot g_1, g_2, \alpha \cdot g_2 \rangle$$

> **Critical Security Requirement**: The secret $\alpha$ must be destroyed after setup. If any party knows $\alpha$, they can forge arbitrary openings.

This is commonly called the **"toxic waste"** problem.

### Commitment Phase

To commit to polynomial $f(X) = \sum_{i=0}^{t} c_i X^i$:

$$C = \sum_{i=0}^{t} c_i \cdot (\alpha^i \cdot g_1) = f(\alpha) \cdot g_1$$

The prover evaluates $f$ at the secret point $\alpha$ "in the exponent" without knowing $\alpha$.

### Opening Phase

To prove $f(x_0) = y$, exploit the factorization:

$$f(X) - f(x_0) = (X - x_0) \cdot q(X)$$

where $q(X)$ is the quotient polynomial of degree $(t-1)$.

The witness is:

$$w = q(\alpha) \cdot g_1$$

### Verification

Verify the opening $\langle x_0, y, w \rangle$ by checking:

$$e(C, g_2) \stackrel{?}{=} e(w, \alpha \cdot g_2 - x_0 \cdot g_2) \cdot e(g_1, g_2)^y$$

This pairing equation verifies the polynomial identity at the secret point $\alpha$.

### Security Assumptions

| Assumption | Description |
|------------|-------------|
| **Discrete Logarithm** | Given $g$ and $h = x \cdot g$, hard to find $x$ |
| **$t$-SDH** | Given $g, \alpha \cdot g, \ldots, \alpha^t \cdot g$, hard to find $\langle c, \frac{1}{\alpha + c} \cdot g \rangle$ |

The $t$-SDH assumption is **stronger** than discrete logarithm and implies both CDH and DLOG hardness.

## IPA with Pedersen Commitments

### Mathematical Foundation

IPA operates over a single elliptic curve group $\mathbb{G}$ of prime order $p$, requiring only standard scalar multiplication—**no pairings**.

### Setup (Transparent)

Generate a vector of independent generators via **hash-to-curve**:

$$\mathbf{G} = [G_0, G_1, \ldots, G_{n-1}]$$

$$Q \text{ (separate generator for IPA)}$$

> **Key Property**: No secret values are created or destroyed. The setup is **transparent** and **deterministic**.

### Pedersen Vector Commitment

To commit to vector $\mathbf{v} = [v_0, v_1, \ldots, v_{n-1}]$:

$$C = \sum_{i=0}^{n-1} v_i \cdot G_i$$

This is an **additively homomorphic** commitment:

$$\text{Commit}(\mathbf{v}) + \text{Commit}(\mathbf{w}) = \text{Commit}(\mathbf{v} + \mathbf{w})$$

### Inner Product Argument

The IPA proves knowledge of vectors $\mathbf{a}$ and $\mathbf{b}$ such that:

$$\langle \mathbf{a}, \mathbf{b} \rangle = c$$

where the inner product is defined as:

$$\langle \mathbf{a}, \mathbf{b} \rangle = \sum_{i=0}^{n-1} a_i \cdot b_i$$

### Recursive Proof Structure

The IPA proceeds by **recursive halving**:

1. Split vectors into left and right halves
2. Compute cross-terms $L$ and $R$
3. Verifier sends random challenge $x$
4. Fold vectors: $\mathbf{a}' = \mathbf{a}_L + x \cdot \mathbf{a}_R$
5. Repeat until vectors have length 1

**Proof size**: $O(\log n)$ group elements

**Verification**: $O(\log n)$ scalar multiplications

### Security Assumption

| Assumption | Description |
|------------|-------------|
| **Discrete Logarithm** | Given $g$ and $h$, hard to find $x$ such that $h = x \cdot g$ |

This is the **most conservative** cryptographic assumption for elliptic curves.

## Comparative Analysis

### Side-by-Side Comparison

| Aspect | KZG | IPA + Pedersen |
|--------|-----|----------------|
| **Algebraic Structure** | Bilinear pairings | Scalar multiplication only |
| **Curve Type** | Pairing-friendly (BLS12-381) | Standard EC (Bandersnatch) |
| **Trusted Setup** | Required (toxic waste) | Not required (transparent) |
| **Security Assumption** | $t$-SDH (stronger) | DLOG only (conservative) |
| **Proof Size** | $O(1)$ — constant ~48 bytes | $O(\log n)$ — ~32 bytes typical |
| **Verification Time** | $O(1)$ — single pairing | $O(\log n)$ — multiple scalar mults |
| **Prover Time** | Fast | Comparable |
| **Aggregation** | Excellent | Good |

### Trusted Setup Implications

```
KZG Setup Ceremony:
┌─────────────────────────────────────────────────────────────┐
│  Participant 1 → Participant 2 → ... → Participant N        │
│       ↓               ↓                    ↓                │
│    α₁ · g          α₂ · (α₁ · g)      αₙ · (... · g)       │
│       ↓               ↓                    ↓                │
│   destroy α₁      destroy α₂          destroy αₙ            │
└─────────────────────────────────────────────────────────────┘
Security: Safe if AT LEAST ONE participant destroys their secret

IPA Setup:
┌─────────────────────────────────────────────────────────────┐
│  Hash("Generator_0") → G₀                                   │
│  Hash("Generator_1") → G₁                                   │
│  ...                                                        │
│  Hash("Generator_n") → Gₙ                                   │
└─────────────────────────────────────────────────────────────┘
Security: Deterministic, verifiable, no secrets
```

### Performance Characteristics

For a Verkle tree with width $w = 256$:

| Operation | KZG | IPA |
|-----------|-----|-----|
| **Proof Size** | 48 bytes | 32 bytes |
| **Verification** | ~2ms (1 pairing) | ~15ms ($\log_2 256 = 8$ rounds) |
| **Proof Generation** | ~5ms | ~10ms |

> **Note**: These are approximate values. Actual performance depends on implementation and hardware.

### Cryptographic Assumption Hierarchy

```
        t-SDH (KZG requires this)
           │
           ▼
         CDH (Computational Diffie-Hellman)
           │
           ▼
        DLOG (IPA requires only this)
           │
           ▼
    Most Conservative
```

IPA's reliance solely on DLOG means it remains secure even if stronger assumptions are broken.

## Why IPA for Academic Credentials

### Long-Term Verifiability

Academic credentials must remain verifiable for **decades**. The trust model matters:

| Scenario | KZG Impact | IPA Impact |
|----------|------------|------------|
| Setup ceremony compromise discovered in 2040 | All credentials potentially forged | Not applicable |
| Advances in pairing cryptanalysis | Security degraded | No impact |
| Need to verify 30-year-old credential | Must trust 2024 ceremony | Independently verifiable |

### Alignment with Ethereum

The `go-verkle` library used in IU-MiCert implements IPA + Pedersen, matching Ethereum's design choice for their state tree migration:

> *"For Ethereum's state tree, we chose IPA over KZG to avoid trusted setup requirements for a system that must operate trustlessly for decades."*
> — Ethereum Verkle Tree EIP

### Practical Considerations

1. **No Ceremony Coordination**: Universities can deploy independently
2. **Auditability**: Anyone can verify the generator derivation
3. **Future-Proof**: Conservative assumptions age better
4. **Sufficient Performance**: Academic verification is not latency-critical
