\chapter{METHODOLOGY}
\label{ch:methodology}

This chapter describes the systematic approach to designing and implementing the IU-MiCert system for verifiable academic credentials. Beginning with high-level system requirements derived from the problem statement, the chapter progresses through requirement analysis, system architecture design, and detailed design specifications for each major component. The methodology emphasizes the separation between system design (what the system does and how components interact) and implementation details (specific algorithms and code), with the latter covered in Chapter 5.

\section{System Requirements}
\label{sec:system-requirements}

The system must fulfill several high-level requirements derived from the problem statement and gaps identified in existing blockchain credential systems.

The system must enable \textbf{granular verification} of individual course completions as independent micro-credentials, rather than requiring verification of complete certificates or transcripts. This addresses the limitation where existing systems such as BlockCerts and IU-TransCert can only verify credentials as atomic units, preventing employers from verifying specific technical skills without accessing complete academic records. To achieve this efficiently, the system must generate \textbf{compact cryptographic proofs} that remain constant in size regardless of the total dataset size. This directly addresses the O(log n) scaling limitation of Merkle tree-based systems where proof sizes grow with tree depth, creating verification overhead and storage burdens that limit scalability. Additionally, the system must provide \textbf{temporal integrity} through cryptographic binding between credentials and their issuance time via blockchain timestamps. This ensures credentials cannot be backdated or manipulated to falsely claim earlier achievements, addressing the temporal proof gap that enables timeline manipulation in current systems.

To address privacy concerns that arise when students must reveal complete transcripts for any verification, the system must support \textbf{selective disclosure}, allowing students to prove specific achievements without revealing their complete academic history. The system must enable filtering of credentials at the receipt level while maintaining cryptographic validity of the remaining proofs, addressing the current limitation where full transcripts must be disclosed even when verifiers need only specific information. This capability must be achieved while maintaining \textbf{cost-effective deployment} by anchoring only compact tree roots (32 bytes per term) on-chain rather than storing individual credential hashes as in systems like CVSS. This design enables scalable deployment where thousands of credentials can be verified through a single on-chain commitment, amortizing blockchain costs across all students in a term rather than incurring per-credential publishing fees.

The system must maintain core blockchain benefits through \textbf{trustless verification}, enabling verifiers to independently validate credentials by checking blockchain-anchored roots and cryptographic proofs without requiring contact with the issuing institution. This decentralized verification model, inherited from blockchain credential systems like BlockCerts, eliminates dependencies on institutional availability and reduces administrative burden. Once issued, credentials must be cryptographically bound to blockchain state such that any tampering or modification is detectable through proof verification failure, ensuring \textbf{immutable credential records} that provide the anti-forgery guarantees essential for academic credential systems. Finally, the system must provide \textbf{revocation support} through version-based tree supersession, allowing institutions to publish updated credential sets while maintaining verifiability of both old and new versions. This addresses scenarios such as academic misconduct, grade corrections, or administrative errors where credentials must be invalidated without invalidating the entire term's credentials or requiring complex revocation list maintenance.

        \item Remove unwanted courses or entire terms from JSON structure

The system follows a three-tier architecture with clear separation of concerns. The \textbf{presentation layer} provides web interfaces for three actors: issuers who manage credential issuance and revocation, students who view and share their receipts, and verifiers who validate credentials. These interfaces abstract the complexity of cryptographic operations and blockchain interactions, providing intuitive user experiences for non-technical users.

The \textbf{application layer} consists of a REST API server implemented in Go that handles business logic and coordinates operations between components. The API server orchestrates credential issuance workflows (data import, tree construction, proof generation), manages verification requests (receipt validation, blockchain queries, proof verification), and processes revocation requests (tree reconstruction, version management, root republication). This layer enforces access control policies, validates input data, and provides error handling for all operations.

The \textbf{data layer} integrates three key components. The Verkle engine, implemented using Ethereum's go-verkle library, constructs and manages Verkle trees for each academic term, computes Pedersen commitments, and generates IPA-based membership proofs. The local database, implemented with PostgreSQL and GORM, stores term data, maintains course completion records, caches pre-computed proofs for efficient receipt generation, and tracks revocation requests through approval workflows. The blockchain component consists of the IUMiCertRegistry smart contract deployed on Ethereum Sepolia testnet, which stores 32-byte term root commitments with version tracking and provides public query interfaces for verification.

\subsubsection{Component Responsibilities}

\textbf{1. Web Portals (Presentation Layer)}

The \textbf{Issuer Dashboard} manages the complete credential issuance workflow. It provides interfaces for uploading course completion data exported from Learning Management Systems, initiating Verkle tree construction for academic terms, triggering root commitment publication to the blockchain, and managing credential revocation requests. The dashboard displays term publication status, shows blockchain transaction confirmations, and provides administrative controls for managing the credential lifecycle.

The \textbf{Student Portal} enables students to access and manage their credential receipts. While the current implementation provides receipt viewing capabilities, the portal is designed to support receipt filtering for selective disclosure, allowing students to create customized receipts containing only the credentials relevant to specific applications. The portal displays verification status and provides guidance on sharing receipts with verifiers.

The \textbf{Verifier Portal} accepts receipt uploads from students or employers and displays verification results. The portal provides an intuitive interface for non-technical users to verify credential authenticity, showing course details, blockchain confirmation status, and version currency indicators. It abstracts the complexity of cryptographic verification and blockchain queries, presenting results through clear visual indicators.

\textbf{2. REST API Server (Application Layer)}

The API server's \textbf{Credential Issuance} subsystem coordinates the complete issuance workflow. It validates uploaded course data, triggers Verkle tree construction through the cryptographic engine, manages proof generation for all students, orchestrates blockchain publishing transactions, and generates student receipts. This subsystem implements business logic for handling issuance errors, validating data integrity, and ensuring atomic transactions.

The \textbf{Verification Service} validates receipt structure and orchestrates cryptographic verification. It parses uploaded receipts, extracts term roots and version information, queries the blockchain smart contract for root validation, invokes the Verkle engine for IPA proof verification, and aggregates results into a comprehensive verification report. The service handles version currency checking, alerting verifiers when receipts reference superseded term versions.

The \textbf{Revocation Management} subsystem processes credential invalidation requests. It maintains a workflow for revocation request submission, review, and approval, then coordinates tree reconstruction for affected terms. Once approved revocations are processed, the subsystem triggers Verkle tree rebuilding with revoked credentials removed, manages version increment logic, publishes updated roots to the blockchain, and generates new receipts reflecting the current credential state.

\textbf{3. Verkle Engine (Data Layer - Cryptographic Core)}

The \textbf{Tree Construction} capability builds Verkle trees from course completion data. For each academic term, the engine creates an empty 256-ary tree, inserts key-value pairs for each course completion (with keys derived from student DID, term ID, and course ID), and computes Pedersen commitments recursively from leaves to root. The final 32-byte root commitment serves as a cryptographic fingerprint of all credentials in the term.

The \textbf{Proof Generation} capability creates membership proofs for individual courses. Using Ethereum's go-verkle library, the engine invokes the MakeVerkleMultiProof function to generate IPA-based proofs demonstrating that a specific course key-value pair exists in the committed tree. Proofs are serialized into two components: the verkle proof (IPA data) and state diff (containing actual course value hashes), then bundled with metadata into the receipt structure.

The \textbf{Proof Verification} capability validates receipts independently. The engine deserializes proofs, recomputes expected hashes from course data, extracts values from state diffs to confirm data integrity, performs IPA verification to validate the cryptographic path from claimed course to root commitment, and returns boolean validation results. This verification is purely cryptographic and does not require access to the original tree.

\textbf{4. Local Database (Data Layer - Persistent Storage)}

\textbf{Term Data Storage} maintains the complete state of constructed Verkle trees. The database stores tree structures in serialized format, maintains course completion records with full metadata (course ID, name, grade, credits, instructor, timestamp), and tracks tree version history for each term. This enables efficient tree loading when generating new receipts or processing revocations.

\textbf{Proof Caching} stores pre-computed proofs for efficient receipt generation. While proofs can be generated on-demand, caching reduces computational overhead when multiple receipts are generated for the same term. The cache is invalidated when term trees are rebuilt due to revocations.

\textbf{Revocation Tracking} records the complete revocation workflow state. The database maintains revocation requests with fields for student ID, course ID, term ID, reason, status (pending/approved/rejected), submission timestamp, and processing timestamp. This provides an audit trail for all revocation activities and enables workflow management through approval processes.

\textbf{5. Blockchain Smart Contract (Data Layer - Public Registry)}

The \textbf{Root Publishing} functionality stores term root commitments with version tracking. The smart contract maintains a two-dimensional mapping from term identifiers and version numbers to 32-byte root commitments. When roots are published, the contract automatically increments the version counter, emits TermRootPublished events containing term ID, version, root, and block timestamp, creating an immutable audit log of all credential publications. Access control modifiers ensure only the authorized issuer can publish roots.

The \textbf{Root Retrieval} functionality provides public query interfaces for verification. The contract exposes view functions (gas-free) that return the root commitment for any term and version combination, as well as functions to query the current version for a term. This enables verifiers to independently check receipt validity without requiring issuer interaction or incurring transaction costs.

\subsubsection{Interaction Flows}

\textbf{Credential Issuance Flow (Steps 1-5):}

Step 1: The issuer uploads course completion data through the dashboard interface. The data, typically exported from an LMS in JSON or CSV format, is transmitted to the API server via HTTP POST request.

Step 2: The API server validates the data structure and forwards it to the Verkle Engine. The engine creates a new empty Verkle tree for the specified term and begins inserting course records.

Step 3: The Verkle Engine processes each course completion, computing key hashes from student DID, term ID, and course ID, computing value hashes from serialized course data, and inserting key-value pairs into the tree structure. Once all courses are inserted, the engine computes the tree commitment, producing a 32-byte root.

Step 4: The API server receives the computed root and stores the complete tree state to the database. The server then generates individual student receipts by collecting each student's courses from the tree and generating Verkle proofs using the engine's proof generation capability. Receipts are stored in the database for distribution.

Step 5: The API server initiates blockchain publication by constructing an Ethereum transaction calling the publishTermRoot function. The transaction includes the term identifier and 32-byte root commitment. Upon blockchain confirmation, the transaction hash is stored in the database, linking the term to its on-chain publication.

\textbf{Credential Verification Flow (Steps 6-8):}

Step 6: A student or verifier uploads a receipt JSON file through the verification portal. The portal transmits the receipt to the API server via HTTP POST.

Step 7: The API server extracts term information from the receipt and forwards it to the Verkle Engine for cryptographic verification. For each course in the receipt, the engine validates the proof by deserializing the Verkle proof, recomputing expected hashes, checking state diff values, performing IPA verification, and confirming the reconstructed root matches the receipt's claimed root.

Step 8: Concurrently with cryptographic verification, the API server queries the blockchain smart contract to retrieve the published root for each term and version in the receipt. The server validates that receipt roots match blockchain roots and checks if the receipt version is current or superseded.

Step 9: The API server aggregates verification results (cryptographic validity and blockchain confirmation) and returns the result to the portal, which displays the outcome with detailed information about verified courses and blockchain anchoring status.

\subsubsection{Data Dependencies}

Component interactions exhibit clear data dependencies that define the system's operational constraints. The Verkle Engine requires course completion data from the API Server to perform tree construction—it cannot operate independently. The API Server must receive the computed root from the Verkle Engine before initiating blockchain publication, as the root is the critical data being anchored. Verification operations require roots from the Blockchain to validate proofs generated by the Verkle Engine—without blockchain-anchored roots, proofs cannot be trusted. The Database serves as the persistence layer for all components except the Blockchain, which maintains its own distributed ledger. This dependency structure ensures proper sequencing of operations and prevents invalid states such as receipt generation before tree commitment or verification before blockchain anchoring.

\section{System Architecture and Design}
\label{sec:system-design}

This section details the data structures, tree organization, and cryptographic mechanisms that enable verifiable micro-credential management.

\subsection{Data Model}
\label{subsec:data-model}

The core data structure in IU-MiCert is the course completion record, which represents a single micro-credential:

\begin{lstlisting}[language=json, caption=Course Completion Record Structure, label=lst:course-record]
{
  "issuer_id": "IU-VNUHCM",
  "student_id": "ITITIU00001",
  "term_id": "Semester_1_2023",
  "course_id": "IT013IU",
  "course_name": "Introduction to Computing",
  "grade": "A",
  "credits": 3,
  "completed_at": "2023-12-15T00:00:00Z",
  "instructor": "Dr. Nguyen Van A"
}
\end{lstlisting}

Each course completion record is converted into a Verkle tree entry through a deterministic key generation scheme and cryptographic hashing:

\textbf{Key Generation:}
\begin{equation}
\text{courseKey} = \text{studentDID}:\text{termID}:\text{courseID}
\end{equation}

Example:
\begin{equation}
\text{courseKey} = \text{``did:example:ITITIU00001:Semester\_1\_2023:IT013IU''}
\end{equation}

This key is then hashed to produce a 32-byte value:
\begin{equation}
\text{keyHash} = \text{SHA256}(\text{courseKey}) = [\text{stem: 31 bytes}][\text{suffix: 1 byte}]
\end{equation}

The course data itself is serialized and hashed:
\begin{equation}
\text{valueHash} = \text{SHA256}(\text{JSON}(\text{courseRecord}))
\end{equation}

This (keyHash, valueHash) pair forms the leaf entry in the Verkle tree. The deterministic key construction ensures that the same course for the same student in the same term always produces the same tree position, enabling reproducible verification.

\subsection{Tree Structure (One per Term)}
\label{subsec:tree-structure}

IU-MiCert employs a single Verkle tree per academic term, aggregating all course completions for all students within that term. This design choice provides several advantages: it enables efficient term-based commitment with a single 32-byte root covering potentially thousands of credentials, supports temporal integrity by associating all credentials in a term with a single blockchain timestamp, and simplifies revocation by allowing term-level tree reconstruction.

\section{Verkle Tree Construction Design}
\label{sec:verkle-construction-design}

The Verkle tree construction process operates on a per-term basis, where each academic term has a dedicated tree containing all course completions for all students in that term. The construction follows a three-phase workflow designed to ensure data integrity and cryptographic soundness.

\textbf{Initialization Phase:} A new Verkle tree structure is created for each term, establishing an empty 256-ary tree with version tracking initialized to version 1. The tree maintains mappings between course identifiers and their corresponding entries to support efficient lookup operations. Additionally, structures for storing pre-computed proof data are initialized to enable efficient receipt generation after tree commitment.

\textbf{Population Phase:} Course completion records are inserted into the tree using the deterministic key generation scheme described in Section \ref{subsec:data-model}. Each course is uniquely identified by combining the student's decentralized identifier (DID), the term identifier, and the course code. These composite keys are hashed to produce 32-byte values that serve as Verkle tree keys, while the course record data is serialized and hashed to produce the corresponding 32-byte tree values. This two-hash design ensures that identical courses for different students occupy different tree positions (due to different student DIDs) while maintaining verifiable linkage to the original course data through the value hash. As courses are inserted, the tree structure dynamically grows, with internal nodes created as needed to accommodate the key space distribution.

\textbf{Commitment Phase:} Once all courses for a term are inserted, the tree undergoes a commitment operation that recursively computes Pedersen commitments for all nodes from leaves to root. At each leaf node, the system commits to the course value hash. At each internal node, the system commits to the 256 child commitments using Pedersen commitment schemes. This recursive computation culminates in a single 32-byte root commitment that cryptographically binds all course data in the term. The root serves as a cryptographic fingerprint: any modification to any course in the tree would produce a different root value, enabling tamper detection. The commitment is timestamped with the computation time, and this timestamp, combined with the blockchain publication timestamp, establishes temporal integrity for all credentials in the term.

\section{Proof Generation and Verification Design}
\label{sec:proof-design}

The proof system enables students to receive portable credential receipts and allows verifiers to independently validate those credentials without institutional contact. The design carefully separates proof generation (issuer-side) from proof verification (verifier-side) to enable trustless verification.

\textbf{Receipt Generation:} Student receipts aggregate credentials across multiple academic terms, providing a complete or partial view of the student's academic history. Each term section in the receipt contains the term identifier, the Verkle root commitment for that term, the version number indicating which tree version the receipt references, the list of courses for that student in that term, and the cryptographic proofs for each course. This structure enables selective disclosure—students can remove entire terms or individual courses from their receipt JSON file, and the remaining proofs will still validate against the blockchain-anchored roots. The receipt format is JSON for human readability and ease of manipulation, allowing students to use standard text editors for filtering without requiring specialized tools.

\textbf{Proof Structure:} Each course proof consists of two critical components that together enable verification. The Verkle proof component contains the IPA-based cryptographic data representing the path from the course leaf to the tree root, generated using Ethereum's go-verkle library through the MakeVerkleMultiProof function. The state diff component contains the actual course data hashes and tree structure information needed to reconstruct the verification path. Additionally, metadata links the proof to the specific course key, enabling independent verification without requiring access to the full tree. This design ensures proofs are self-contained: a verifier needs only the proof, the course data, and the blockchain-published root to perform complete verification.

\textbf{Verification Process:} Verification operates in two distinct phases that together ensure credential authenticity. The root verification phase queries the blockchain smart contract to retrieve the published term root for the claimed version in the receipt, confirming that the issuer legitimately published this tree commitment. If the root does not exist on-chain, verification immediately fails. The cryptographic verification phase validates each course proof independently by recomputing the expected hashes from the presented course data, extracting the corresponding values from the state diff component, and performing IPA verification to confirm that the proof correctly links the course data to the published root. Each course must pass both root verification (root exists on blockchain) and cryptographic verification (proof validates) for the overall verification to succeed. This two-phase approach ensures credentials are both legitimately issued and unmodified since issuance.

\section{Blockchain Integration Design}
\label{sec:blockchain-design}

The blockchain layer provides immutable, publicly-verifiable storage of term root commitments through an Ethereum smart contract. The contract design emphasizes minimal on-chain storage while supporting credential versioning for revocation scenarios.

\textbf{Data Storage Model:} The smart contract maintains a two-dimensional mapping structure where term identifiers map to versioned root commitments. Formally, the mapping is:

\begin{equation}
\text{termRoots}: \text{termIDHash} \times \text{version} \rightarrow \text{root32bytes}
\end{equation}

Each term can have multiple versions (v1, v2, v3, ...), with the contract tracking both the complete version history and the current active version through a separate mapping. Term identifiers are hashed using Keccak256 before storage to optimize gas costs and provide consistent key sizes, while roots remain as 32-byte values for direct cryptographic verification.

\textbf{Publishing Mechanism:} Only the authorized issuer (university) can publish term roots, enforced through Solidity access control modifiers that check the sender address against the registered issuer address. When a new root is published, whether initial publication or supersession due to revocation, the contract automatically increments the version number for that term. The contract stores the root commitment associated with the new version and emits a TermRootPublished event containing the term identifier hash, version number, root value, and block timestamp. These events provide an auditable, immutable history of all credential publications that can be queried through blockchain explorers or indexed by application-layer services. The automatic versioning eliminates the need for complex revocation registries—superseded roots remain on-chain as historical records while the current version points to the latest valid credential set.

\textbf{Verification Interface:} The contract exposes read-only query functions that allow anyone to retrieve root commitments without transaction costs. The primary verification function accepts a term identifier and version number, returning the corresponding 32-byte root commitment if it exists or zero if no such root was published. A complementary function returns the current version number for a term, enabling verifiers to check if a receipt references an outdated tree version. These view functions are gas-free, making verification accessible without requiring cryptocurrency holdings or transaction fees. The public nature of these functions aligns with the trustless verification requirement—any party can independently validate credentials by querying the smart contract.

\section{Credential Revocation System Design}
\label{sec:revocation-design}

The credential revocation system addresses scenarios where credentials must be invalidated post-issuance, such as academic misconduct discovery, grade corrections, or administrative errors. The design employs version-based supersession rather than traditional revocation lists.

\subsection{Revocation Approach: Version-Based Supersession}
\label{subsec:version-supersession}

Instead of marking individual credentials as revoked through separate registry contracts or revocation lists, IU-MiCert publishes a new version of the affected term tree that excludes the revoked credentials. This approach provides several advantages: it avoids the complexity of maintaining separate revocation registries, enables batch revocation processing where multiple credentials can be revoked in a single tree reconstruction, and maintains cryptographic consistency since all credentials in the new version validate against the new root.

Figure \ref{fig:revocation-concept} illustrates the version-based supersession concept:

\begin{figure}[H]
\centering
\includegraphics[width=0.9\textwidth]{figures/revocation_versioning.png}
\caption{Version-Based Revocation Through Tree Supersession}
\label{fig:revocation-concept}
\end{figure}

When verifiers receive a receipt referencing version 1, they query the blockchain and discover that version 2 is current. The system alerts the verifier that a newer credential set exists, allowing policy-based decisions about whether to accept the superseded receipt or require updated credentials.

\subsection{Revocation Workflow}
\label{subsec:revocation-workflow}

The revocation workflow involves multiple stages with appropriate approvals to prevent unauthorized credential invalidation. A revocation request is submitted through the issuer dashboard, specifying the student identifier, course identifier, term identifier, and reason for revocation. The request enters a pending state in the database. Authorized administrators review the request, verify supporting documentation, and approve or reject the revocation through the dashboard interface. Once approved, the system processes the revocation by loading the current term tree, removing the specified course credential, rebuilding the tree with the remaining credentials, computing a new root commitment, incrementing the term version, publishing the new root to the blockchain, and generating updated receipts for affected students. This workflow ensures accountability through approval requirements and maintains an audit trail of all revocation activities.

\subsection{Verification with Revocation}
\label{subsec:verification-revocation}

When verifiers receive a credential receipt, they must consider version currency in addition to cryptographic validity. The verification process compares the receipt's term version against the blockchain's current version for that term. If a receipt presents version 1 but the blockchain indicates version 2 as current, the verifier is alerted that a newer credential set exists. The system design allows verifiers to make policy-based decisions: they may accept the older proof as still cryptographically valid (since the v1 root remains on-chain), warn the credential holder about the superseded version, or require presentation of credentials from the latest version. This flexibility accommodates different verification contexts—some scenarios may accept historical credentials while others require current versions. The approach maintains cryptographic integrity across all versions since each version's root remains anchored on the blockchain.
