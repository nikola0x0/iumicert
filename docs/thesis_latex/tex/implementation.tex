\section{Verkle Tree Construction Implementation}
\label{sec:verkle-impl}

This section presents the actual algorithms implemented for Verkle tree construction, using formal pseudocode notation supplemented with Go code examples from the implementation.

\subsection{Tree Initialization Algorithm}
\label{subsec:tree-init-algo}

The tree initialization establishes the data structure for managing a term's credentials.

\begin{algorithm}[H]
\caption{NewTermVerkleTree - Initialize Term Tree}
\label{alg:new-term-tree}
\begin{algorithmic}[1]
\STATE \textbf{function} NewTermVerkleTree(termID: string) $\rightarrow$ TermVerkleTree
\STATE \quad tree $\leftarrow$ new empty Verkle tree using verkle.New()
\STATE \quad entries $\leftarrow$ empty map[string]CourseCompletion
\STATE \quad proofs $\leftarrow$ empty map[string][]byte
\STATE \quad \textbf{return} TermVerkleTree \{
\STATE \quad \quad TermID: termID,
\STATE \quad \quad Version: 1,
\STATE \quad \quad CourseEntries: entries,
\STATE \quad \quad CourseProofs: proofs,
\STATE \quad \quad tree: tree
\STATE \quad \}
\STATE \textbf{end function}
\end{algorithmic}
\end{algorithm}

\textbf{Implementation Details:} The function creates a new TermVerkleTree structure for a specific academic term. Version tracking starts at 1 for initial publication. The CourseEntries map enables efficient lookup of course metadata during receipt generation. The CourseProofs map caches generated proofs to avoid redundant computation. The underlying Verkle tree is instantiated using Ethereum's go-verkle library through the \texttt{verkle.New()} function.

\subsection{Course Insertion Algorithm}
\label{subsec:course-insertion-algo}

The course insertion algorithm adds individual course completions to the term tree.

\begin{algorithm}[H]
\caption{AddCourses - Insert Student Courses into Tree}
\label{alg:add-courses}
\begin{algorithmic}[1]
\STATE \textbf{function} AddCourses(studentDID: string, courses: []CourseCompletion)
\FOR{each course in courses}
    \STATE courseKey $\leftarrow$ studentDID || ":" || termID || ":" || course.CourseID
    \STATE \COMMENT{Example: "did:example:ITITIU00001:Semester\_1\_2023:IT013IU"}
    \STATE
    \STATE keyHash $\leftarrow$ SHA256(courseKey)
    \STATE \COMMENT{Split into [stem: 31 bytes][suffix: 1 byte]}
    \STATE
    \STATE courseJSON $\leftarrow$ JSON.Serialize(course)
    \STATE valueHash $\leftarrow$ SHA256(courseJSON)
    \STATE
    \STATE tree.Insert(keyHash, valueHash)
    \STATE \COMMENT{Insert into Verkle tree using go-verkle Insert() method}
    \STATE
    \STATE CourseEntries[courseKey] $\leftarrow$ course
    \STATE \COMMENT{Store course data for later access}
\ENDFOR
\STATE \textbf{end function}
\end{algorithmic}
\end{algorithm}

\textbf{Key Implementation Decisions:}
\begin{itemize}
    \item \textbf{Deterministic key generation} ensures that the same course for the same student in the same term always produces the same tree position, enabling reproducibility
    \item \textbf{SHA256 hashing} is used for both keys and values to provide consistent 32-byte outputs compatible with Verkle tree requirements
    \item \textbf{Stem/suffix split} aligns with Verkle tree's internal addressing scheme where stems identify tree paths and suffixes identify specific positions within nodes
    \item \textbf{Course data stored separately} from the tree enables metadata access during receipt generation without tree traversal
\end{itemize}

\subsection{Tree Commitment Algorithm}
\label{subsec:tree-commitment-algo}

The commitment algorithm computes the cryptographic root binding all courses in a term.

\begin{algorithm}[H]
\caption{PublishTerm - Compute Tree Commitment}
\label{alg:publish-term}
\begin{algorithmic}[1]
\STATE \textbf{function} PublishTerm() $\rightarrow$ VerkleRoot
\STATE \quad commitment $\leftarrow$ tree.Commit()
\STATE \quad \COMMENT{Recursively computes Pedersen commitments for all nodes}
\STATE
\STATE \quad VerkleRoot $\leftarrow$ commitment.Bytes()
\STATE \quad \COMMENT{Converts elliptic curve point to 32-byte array}
\STATE
\STATE \quad PublishedAt $\leftarrow$ time.Now()
\STATE \quad \COMMENT{Records commitment computation timestamp}
\STATE
\STATE \quad \textbf{return} VerkleRoot
\STATE \textbf{end function}
\end{algorithmic}
\end{algorithm}

\textbf{Implementation Notes:} The \texttt{Commit()} operation from go-verkle traverses the tree bottom-up. At each leaf, it commits to the value hash. At each internal node, it commits to the 256 child commitments using Pedersen commitment scheme: $C = g^{m_1} \cdot h^{m_2} \cdot \ldots$ where $g, h, \ldots$ are generator points. The final root commitment cryptographically binds all course data in the term—any modification to any course would produce a different root.

\section{Proof Generation and Verification Implementation}
\label{sec:proof-impl}

This section presents the algorithms for generating student receipts and verifying credentials.

\subsection{Receipt Generation Algorithm}
\label{subsec:receipt-generation-algo}

The receipt generation algorithm creates a complete credential package for a student across multiple terms.

\begin{algorithm}[H]
\caption{GenerateStudentReceipt - Create Complete Receipt}
\label{alg:generate-receipt}
\begin{algorithmic}[1]
\STATE \textbf{function} GenerateStudentReceipt(studentID: string) $\rightarrow$ StudentReceipt
\STATE \quad terms $\leftarrow$ []
\STATE
\STATE \quad \textbf{for each} termTree in allTermTrees \textbf{do}
\STATE \quad \quad \textbf{if} termTree.hasCoursesForStudent(studentID) \textbf{then}
\STATE \quad \quad \quad terms.append(termTree.TermID)
\STATE \quad \quad \textbf{end if}
\STATE \quad \textbf{end for}
\STATE
\STATE \quad termReceipts $\leftarrow$ []
\STATE \quad \textbf{for each} term in terms \textbf{do}
\STATE \quad \quad proofs $\leftarrow$ empty map
\STATE \quad \quad courses $\leftarrow$ term.getStudentCourses(studentID)
\STATE
\STATE \quad \quad \textbf{for each} course in courses \textbf{do}
\STATE \quad \quad \quad proof $\leftarrow$ GenerateCourseProof(studentID, course.ID, termTree)
\STATE \quad \quad \quad proofs[course.ID] $\leftarrow$ proof
\STATE \quad \quad \textbf{end for}
\STATE
\STATE \quad \quad termReceipt $\leftarrow$ \{
\STATE \quad \quad \quad term\_id: termTree.TermID,
\STATE \quad \quad \quad verkle\_root: termTree.VerkleRoot,
\STATE \quad \quad \quad version: termTree.Version,
\STATE \quad \quad \quad courses: courses,
\STATE \quad \quad \quad proofs: proofs
\STATE \quad \quad \}
\STATE \quad \quad termReceipts.append(termReceipt)
\STATE \quad \textbf{end for}
\STATE
\STATE \quad \textbf{return} \{
\STATE \quad \quad student\_id: studentID,
\STATE \quad \quad generated\_at: timestamp,
\STATE \quad \quad terms: termReceipts
\STATE \quad \}
\STATE \textbf{end function}
\end{algorithmic}
\end{algorithm}

This algorithm aggregates all terms where the student has course completions and generates proofs for each course, creating a comprehensive receipt that enables full or partial credential verification.

\subsection{Individual Proof Generation Algorithm}
\label{subsec:proof-gen-algo}

The individual proof generation uses go-verkle's multiproof functionality.

\begin{algorithm}[H]
\caption{GenerateCourseProof - Generate Single Course Proof}
\label{alg:generate-course-proof}
\begin{algorithmic}[1]
\STATE \textbf{function} GenerateCourseProof(studentDID, courseID, termTree) $\rightarrow$ ProofBundle
\STATE \quad courseKey $\leftarrow$ studentDID || ":" || termTree.TermID || ":" || courseID
\STATE \quad keyHash $\leftarrow$ SHA256(courseKey)
\STATE
\STATE \quad proof, \_, \_, \_, err $\leftarrow$ MakeVerkleMultiProof(
\STATE \quad \quad tree: termTree.tree,
\STATE \quad \quad preState: nil, \COMMENT{Current state only - membership proof}
\STATE \quad \quad keys: [keyHash], \COMMENT{Single key to prove}
\STATE \quad \quad resolver: nil \COMMENT{No external resolver needed}
\STATE \quad )
\STATE
\STATE \quad \textbf{if} err $\neq$ nil \textbf{then}
\STATE \quad \quad \textbf{return} error
\STATE \quad \textbf{end if}
\STATE
\STATE \quad verkleProof, stateDiff, \_ $\leftarrow$ SerializeProof(proof)
\STATE \quad \COMMENT{verkleProof: IPA proof data; stateDiff: leaf values}
\STATE
\STATE \quad \textbf{return} \{
\STATE \quad \quad verkle\_proof: verkleProof,
\STATE \quad \quad state\_diff: stateDiff,
\STATE \quad \quad course\_key: courseKey,
\STATE \quad \quad course\_id: courseID
\STATE \quad \}
\STATE \textbf{end function}
\end{algorithmic}
\end{algorithm}

\textbf{Implementation Details:} The \texttt{MakeVerkleMultiProof} function from Ethereum's go-verkle library generates an IPA-based proof showing the path from the specified key to the tree root. The proof is self-contained and can be verified independently without access to the original tree. The \texttt{SerializeProof} function converts the proof structure into a format suitable for JSON serialization and transmission in receipts.

\subsection{Proof Verification Algorithm}
\label{subsec:proof-verify-algo}

The verification algorithm validates a single course credential.

\begin{algorithm}[H]
\caption{VerifyCourseProof - Validate Course Credential}
\label{alg:verify-course-proof}
\begin{algorithmic}[1]
\STATE \textbf{function} VerifyCourseProof(courseKey, course, proofData, verkleRoot) $\rightarrow$ boolean
\STATE \quad proofBundle $\leftarrow$ Deserialize(proofData)
\STATE
\STATE \quad \textbf{if} courseKey $\neq$ proofBundle.CourseKey \textbf{then}
\STATE \quad \quad \textbf{return} false \COMMENT{Metadata validation failed}
\STATE \quad \textbf{end if}
\STATE
\STATE \quad keyHash $\leftarrow$ SHA256(courseKey)
\STATE \quad valueHash $\leftarrow$ SHA256(JSON(course))
\STATE
\STATE \quad stem $\leftarrow$ keyHash[0:31]
\STATE \quad suffix $\leftarrow$ keyHash[31]
\STATE
\STATE \quad \textbf{for each} entry in proofBundle.StateDiff \textbf{do}
\STATE \quad \quad \textbf{if} entry.stem = stem \textbf{then}
\STATE \quad \quad \quad \textbf{if} entry.values[suffix] $\neq$ valueHash \textbf{then}
\STATE \quad \quad \quad \quad \textbf{return} false \COMMENT{Value mismatch - data tampered}
\STATE \quad \quad \quad \textbf{end if}
\STATE \quad \quad \quad \textbf{break}
\STATE \quad \quad \textbf{end if}
\STATE \quad \textbf{end for}
\STATE
\STATE \quad proof $\leftarrow$ DeserializeProof(proofBundle.VerkleProof)
\STATE \quad reconstructedRoot $\leftarrow$ VerifyVerkleProof(proof, keyHash, valueHash)
\STATE
\STATE \quad \textbf{if} reconstructedRoot $\neq$ verkleRoot \textbf{then}
\STATE \quad \quad \textbf{return} false \COMMENT{IPA verification failed}
\STATE \quad \textbf{end if}
\STATE
\STATE \quad \textbf{return} true \COMMENT{All checks passed}
\STATE \textbf{end function}
\end{algorithmic}
\end{algorithm}

\textbf{Critical Verification Steps:}
\begin{itemize}
    \item \textbf{Metadata validation} ensures the proof actually corresponds to the claimed course
    \item \textbf{Hash recomputation} prevents data tampering by verifying course data matches what was committed
    \item \textbf{StateDiff check} confirms the correct value is included in the proof
    \item \textbf{IPA verification} proves the cryptographic path from course to root is valid
\end{itemize}

\subsection{Full Receipt Verification Algorithm}
\label{subsec:receipt-verify-algo}

The full receipt verification validates all credentials across all terms in a student receipt.

\begin{algorithm}[H]
\caption{VerifyReceiptOffChain - Complete Receipt Validation}
\label{alg:verify-receipt}
\begin{algorithmic}[1]
\STATE \textbf{function} VerifyReceiptOffChain(receiptJSON, blockchainRoots) $\rightarrow$ Result
\STATE \quad result $\leftarrow$ \{valid: true, verifiedTerms: [], errors: []\}
\STATE
\STATE \quad \textbf{for each} term in receiptJSON.terms \textbf{do}
\STATE \quad \quad expectedRoot $\leftarrow$ blockchainRoots[term.term\_id][term.version]
\STATE
\STATE \quad \quad \textbf{if} expectedRoot = nil \textbf{then}
\STATE \quad \quad \quad result.valid $\leftarrow$ false
\STATE \quad \quad \quad result.errors.append("Term root not found on blockchain")
\STATE \quad \quad \quad \textbf{continue}
\STATE \quad \quad \textbf{end if}
\STATE
\STATE \quad \quad \textbf{if} term.verkle\_root $\neq$ expectedRoot \textbf{then}
\STATE \quad \quad \quad result.valid $\leftarrow$ false
\STATE \quad \quad \quad result.errors.append("Root mismatch for " || term.term\_id)
\STATE \quad \quad \quad \textbf{continue}
\STATE \quad \quad \textbf{end if}
\STATE
\STATE \quad \quad \textbf{for each} course in term.courses \textbf{do}
\STATE \quad \quad \quad courseKey $\leftarrow$ receiptJSON.student\_id || ":" || term.term\_id || ":" || course.course\_id
\STATE \quad \quad \quad proof $\leftarrow$ term.proofs[course.course\_id]
\STATE
\STATE \quad \quad \quad valid $\leftarrow$ VerifyCourseProof(courseKey, course, proof, term.verkle\_root)
\STATE
\STATE \quad \quad \quad \textbf{if} not valid \textbf{then}
\STATE \quad \quad \quad \quad result.valid $\leftarrow$ false
\STATE \quad \quad \quad \quad result.errors.append("Proof failed for " || course.course\_id)
\STATE \quad \quad \quad \quad \textbf{break}
\STATE \quad \quad \quad \textbf{end if}
\STATE \quad \quad \textbf{end for}
\STATE
\STATE \quad \quad \textbf{if} no errors for this term \textbf{then}
\STATE \quad \quad \quad result.verifiedTerms.append(term.term\_id)
\STATE \quad \quad \textbf{end if}
\STATE \quad \textbf{end for}
\STATE
\STATE \quad \textbf{return} result
\STATE \textbf{end function}
\end{algorithmic}
\end{algorithm}

\textbf{Verification Guarantees:} This two-phase verification (blockchain validation + cryptographic proof validation) ensures that credentials are both legitimately issued (root exists on blockchain) and unmodified since issuance (proofs validate against root). Any failure in either phase results in overall verification failure, maintaining strong security guarantees.

\section{Smart Contract Implementation}
\label{sec:smart-contract-impl}

The IUMiCertRegistry smart contract provides the blockchain infrastructure for storing term root commitments with version tracking.

\subsection{Contract Source Code}
\label{subsec:contract-code}

Listing \ref{lst:smart-contract} presents the complete Solidity implementation:

\begin{lstlisting}[language=Solidity, caption=IUMiCertRegistry Smart Contract, label=lst:smart-contract]
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.19;

contract IUMiCertRegistry {
    address public issuer;

    // termIdHash => version => root (32 bytes)
    mapping(bytes32 => mapping(uint256 => bytes32)) public termRoots;

    // termIdHash => current version number
    mapping(bytes32 => uint256) public currentVersion;

    event TermRootPublished(
        bytes32 indexed termIdHash,
        uint256 version,
        bytes32 root,
        uint256 timestamp
    );

    constructor() {
        issuer = msg.sender;
    }

    modifier onlyIssuer() {
        require(msg.sender == issuer, "Not authorized issuer");
        _;
    }

    function publishTermRoot(
        string calldata termId,
        bytes32 root
    ) external onlyIssuer {
        bytes32 termIdHash = keccak256(bytes(termId));
        uint256 newVersion = currentVersion[termIdHash] + 1;

        termRoots[termIdHash][newVersion] = root;
        currentVersion[termIdHash] = newVersion;

        emit TermRootPublished(
            termIdHash,
            newVersion,
            root,
            block.timestamp
        );
    }

    function getTermRoot(
        string calldata termId,
        uint256 version
    ) external view returns (bytes32) {
        bytes32 termIdHash = keccak256(bytes(termId));
        return termRoots[termIdHash][version];
    }

    function getCurrentVersion(
        string calldata termId
    ) external view returns (uint256) {
        return currentVersion[keccak256(bytes(termId))];
    }
}
\end{lstlisting}

\textbf{Contract Deployment:} The contract is deployed at address \texttt{0x2452F0063c600BcFc232cC9daFc48B7372472f79} on Ethereum Sepolia testnet. The deployment was performed on November 27, 2025, and the contract has been used to publish term roots for all test academic terms.

\section{Revocation System Implementation}
\label{sec:revocation-impl}

The revocation system implementation consists of database schema for tracking requests and workflow implementation for processing revocations.

\subsection{Database Schema}
\label{subsec:revocation-schema}

The revocation system uses two primary database tables:

\begin{lstlisting}[language=SQL, caption=Revocation Database Schema, label=lst:revocation-schema]
CREATE TABLE revocation_requests (
    id INTEGER PRIMARY KEY,
    term_id TEXT NOT NULL,
    student_id TEXT NOT NULL,
    course_id TEXT NOT NULL,
    reason TEXT,
    status TEXT DEFAULT 'pending',
    created_at DATETIME,
    processed_at DATETIME
);

CREATE TABLE term_versions (
    id INTEGER PRIMARY KEY,
    term_id TEXT NOT NULL,
    version INTEGER NOT NULL,
    verkle_root TEXT NOT NULL,
    tx_hash TEXT,
    published_at DATETIME
);
\end{lstlisting}

The \texttt{revocation\_requests} table tracks the complete lifecycle of revocation requests from submission through processing. The \texttt{term\_versions} table maintains a complete history of all published tree versions with their corresponding blockchain transaction hashes.

\subsection{Revocation Processing Flow}
\label{subsec:revocation-processing}

The revocation workflow implementation consists of several stages:

\begin{enumerate}
    \item \textbf{Request Creation:} POST to \texttt{/api/issuer/revocations} creates a new revocation request with status ``pending''
    \item \textbf{Review and Approval:} POST to \texttt{/api/issuer/revocations/\{id\}/approve} moves request to ``approved'' status
    \item \textbf{Batch Processing:} POST to \texttt{/api/issuer/revocations/process} executes:
    \begin{enumerate}
        \item Load current term tree from database
        \item Remove all approved revoked courses
        \item Rebuild tree structure with remaining courses
        \item Compute new root commitment
        \item Increment version number
        \item Publish new root to blockchain via smart contract
        \item Generate new receipts for all students in affected term
        \item Update request status to ``processed''
    \end{enumerate}
\end{enumerate}

The implementation includes comprehensive test coverage for critical operations. A representative test case for full IPA verification:

\begin{lstlisting}[language=Go, caption=Full IPA Verification Test, label=lst:ipa-test]
func TestFullIPAVerification(t *testing.T) {
    // 1. Create term tree
    termTree := NewTermVerkleTree("TestTerm_2024")

    // 2. Add courses for test student
    termTree.AddCourses(studentDID, courses)

    // 3. Publish (compute root commitment)
    termTree.PublishTerm()

    // 4. Generate proof for specific course
    proofData, err := termTree.GenerateCourseProof(

    // 5. Verify proof against computed root
    err = VerifyCourseProof(
        courseKey,
